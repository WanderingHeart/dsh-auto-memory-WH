# 记忆质量与写入口径（v0.6.0 开发线）

这份文档回答三个问题：**什么值得写进长期记忆、写成什么样、如何复查**。它对应 roadmap 1.8 的第 1、2、7 项，也是“质量体检”提示的依据。

## 1. 规则分层：三层各放各的

| 层 | 放什么 | 不放什么 | 载体 |
| --- | --- | --- | --- |
| 硬规则 | 违反就会出错的操作约束（只许用某个 CLI、不许提交 `.work`、验收步骤） | 偏好、一次性结论 | 项目 `AGENTS.md` |
| 长期记忆 | 偏好、决策及其原因、跨会话仍需知道的事实 | 临时任务、单次实验数据、可从代码直接读到的内容 | `~/.dsh/memory-wh`（自动记录/已确认） |
| 阶段报告 | 某次实验、某次发布、某天的观察 | 需要未来会话默认知道的内容 | `docs/progress/` |

判断口诀：**“下个会话不知道会不会出错？”** 会，就写长期记忆；只是留痕，就写报告；是操作禁令，写 `AGENTS.md`。

## 2. 一条记录只表达一个决策

- 名称：主题化 kebab-case，能被人一眼检索到，例如 `release-cadence-one-version-per-acceptance`；避免 `memo`、`notes`、`todo`、`temp` 这类通用名。
- 描述：**只有 description 进入索引**，控制在 240 字符以内，写一句结论即可，例如“每个小版本先切版并在隔离环境验收 21 步再进入下一版本”。
- 正文：写“结论 + 原因 + 边界”。原因解释为什么这样选，边界说明何时不适用；两者是未来会话最需要的部分。
- 拆分：正文出现 4 个以上二级标题，通常意味着混了多个主题，应拆成多条记录。
- 完整性指纹只覆盖 name/title/description/type/body：改描述或正文会更新指纹；改任务时间字段（dueAt/remindAt/priority/taskStatus）不影响指纹。

## 3. 什么不值得写

- 一次性任务：写阶段报告或当日总结即可。
- 代码里已经写明的事实（函数签名、配置默认值）：直接读代码更可靠，记忆容易过期。
- 大段日志、完整对话：只摘结论与原因。
- 猜测：不确定的内容写进记忆会以“已验证”身份误导后续会话；先放候选，等确认。

## 4. 什么时候写

- 用户明确说“记住/以后都这样”时。
- 做出一个以后会反复引用的决策，且原因不在代码注释里时。
- 发现一个会重复踩的坑，并已确认修法时。

写入默认是 **candidate**（1.0.0-rc.10 起直接参与注入，不再需要审核）。模型不能自行授予 verified。

## 5. 质量体检（v0.6.0）

管理面板 → “质量体检”，或调用 `quality.report` API。它只读，不修改记录，返回：

| code | 含义 | 建议动作 |
| --- | --- | --- |
| `description-long` | 描述超过 240 字符 | 细节移入正文，描述只留结论 |
| `body-short` | 正文少于 40 字符 | 补原因与边界，否则未来会话无法判断适用性 |
| `name-generic` | 名称过于通用 | 改成主题化名称 |
| `title-missing` | 普通记忆没有标题 | 补一个能出现在索引里的标题 |
| `task-missing-due` | 进行中的任务没有截止时间 | 补 `dueAt`，或改回普通记忆 |
| `task-overdue` | 任务逾期超过 7 天 | 完成/取消/改期，避免长期占用提醒段 |
| `stale-record` | 记录 180 天未更新 | 确认仍成立后更新，或标记 superseded |
| `body-many-sections` | 正文二级标题超过 4 个 | 拆成多条记录 |

阈值集中在 `src/quality.ts` 顶部，后续按真实一周使用记录调整。

## 6. 检索与召回

- 新会话优先 `memory_list` 了解目录，再 `memory_search` 找具体主题；不要一上来读整库。
- `memory_search` 现在返回 `matchedIn`（name/title/description/body），用于解释“为什么召回这条”；分数只是排序参考，不代表性或权威性。
- 只有 verified 且未静音的记录进入默认注入；候选、争议、被取代的记录不会自动出现。

## 7. 索引预算

- 只有 verified、未静音、非任务记录的标题与描述进入索引，预算由配置 `maxBytes` 控制。
- 保留顺序是确定的：`pinned` 置顶 → 其余按 `importance × 0.995^距上次阅读/更新时间的天数` 降序 → 同分按名称；预算不足时先从尾部截断，并记录被排除原因。
- 描述过长、pinned 过多都会挤占预算；预算不足时注入会截断并在组装审计里记录 `excluded` 原因。面板“质量体检”会显示当前字节/预算与排除明细（含记录名与原因）。
- 定期看面板“存储与审计状态”的索引预算与审计记录，而不是等注入变少才排查。

## 8. 复查节奏

- 每周：看一次质量体检与近重复提示，处理 `warn` 项。
- 每月：抽查 `stale-record`，确认事实仍成立。
- 版本发布前：确认没有 `task-missing-due`、没有超过预算、没有 disputed/superseded 却被引用的记录。

## 9. 度量基线

每日/每周可运行只读采样脚本：

```bash
node --experimental-strip-types scripts/verification/quality-baseline.mjs
```

输出写入 `docs/evidence/S05-v060-quality/baseline.json`（不写任何记忆文件）。采集项：

- 记录数，按 scope/type/status 分布；
- 质量体检 `flagged` 比例与按 code 分布；
- 近重复组数（阈值 0.8，同 type）；
- 索引字节 / 预算比例、被预算排除的条数；
- 召回命中：抽样“搜索后打开并引用”的次数（人工记录）。
