## 1. 动机

r134 之前，同步协议只有“端点契约 + 本地桩”：信封怎么产生、怎么校验都齐了，但两端之间没有一条真实链路——演练都是把信封对象直接交给对方进程。

第 5 项补的就是这条链路，同时保持一个原则：**传输层只搬运不透明字节**。发送方身份、收件人绑定、防篡改、加密都已在 `wh-sync-envelope` 里，中继不需要也不应该理解记忆内容。这样载体可以替换（HTTP、对象存储、未来的移动端推送），协议不用改。

## 2. 实现

### 2.1 客户端（`src/transport.ts`）

```ts
interface SyncTransport {
  publish(envelope: SyncEnvelope): Promise<PublishResult>   // { id, duplicate }
  pull(recipient: string, options?: { limit?: number }): Promise<RelayMessage[]>
  ack(recipient: string, ids: string[]): Promise<AckResult> // { acked }
  stats(): Promise<TransportStats>                          // { queued }
}
```

- `createHttpTransport({ baseUrl, token, timeoutMs?, fetchImpl? })`：校验 `http(s)` 前缀与 token 长度（≥16），用 `AbortController` 做超时（默认 10s）。
- 消息 id = `msg-` + `sha256(canonicalJson(envelope))` 前 32 hex；同一信封重发命中同一条队列项。
- 错误统一为 `TransportError`，`code` ∈ `TRANSPORT_UNAUTHORIZED | UNAVAILABLE | TIMEOUT | REJECTED | BACKPRESSURE | BAD_RESPONSE`，附带 HTTP 状态与服务端错误码。

### 2.2 中继（`src/sync-relay.ts`）

```ts
createRelayServer({ token, root, host?, port?, retentionMs?, maxQueuePerRecipient?, maxBodyBytes?, now? })
  → { start(), stop(), address(), stats() }
```

| 方法与路径 | 作用 |
| --- | --- |
| `POST /v1/messages` | 投递信封；结构校验、幂等、队列上限 |
| `GET /v1/messages?recipient=&limit=` | 按到达顺序拉取该收件人的消息 |
| `POST /v1/ack` | 删除已应用的消息 |
| `GET /v1/health` | 队列数与保留期 |

- 共享 bearer token（常量时间比较），默认只绑定 `127.0.0.1`；token 即信任边界，不是每设备授权。
- 队列按收件人隔离，落盘 `<root>/queue/<recipient>/<msg-id>.json`（临时文件 + rename）；默认保留 7 天、每收件人 500 条、请求体 16 MiB、信封 12 MiB。
- 不解密、不记录信封内容；只保存密文与路由元数据。

### 2.3 发送游标与同步流程（`src/sync.ts`、`src/endpoint.ts`、`src/sync-flow.ts`）

- `SyncState` 增加 `sentCursor?: number`：最后成功发布给对端的 `until`。它与接收游标 `cursor` 独立，应用对端变更不会抹掉它。
- 游标改为**排他水位**：`buildChangeset` 用 `> since` 过滤。否则 `until` 那条记录会在下次推送时被永久重发。
- `SyncEndpoint.recordSent(until)`：只在 `transport.publish` 成功（含幂等命中）后调用，取 `max(旧值, until)`。
- `pushToPeer(endpoint, transport, recipient)`：无新变更不发请求；返回 `{ published, since, until, records, messageId?, duplicate? }`。
- `pullFromPeer(endpoint, transport, { limit?, onConflict? })`：逐条 `apply`，成功项才 `ack`；失败项留在队列并出现在 `failed`，避免毒消息被静默丢弃。

### 2.4 CLI（`src/maintenance-cli.ts`）

新增三个命令，参数表已同步到 `docs/storage-recovery.md`：

- `sync-push`：`root`、`scope`、`identityFile`、`trustFile`、`relayUrl`、`token`、`recipient`；
- `sync-pull`：同上，另可给 `limit`/`onConflict`；
- `sync-relay`：`root`、`token`，可选 `host`/`port`/`retentionMs`；启动后打印 `{ host, port, url }`，SIGINT/SIGTERM 停止。

## 3. 验证

### 传输测试 `tests/transport.spec.ts`（12 项）

中继往返、错误 token、同一信封重复发布（`duplicate: true` 且 id 相同）、队列满 429、超大信封拒绝、保留期过期、ack 未知 id、收件人隔离、重启后队列持久化、发送游标不重发同一尾部、毒消息留队不 ack、错误类型是 `TransportError`。

首跑 9 项失败，原因是中继把整个请求体当成信封交给 `verifyEnvelope`；改为读取 `body.envelope` 后全部通过。这个 bug 说明“协议对、接线错”只有端到端测试能抓住。

### HTTP 演练 `scripts/verification/sync-http-drill.mjs`（14/14 PASS）

本机回环中继上跑完整链路：启动中继 → 空队列 health → A 推送 2 条记录 → 游标推进 → B 拉取并应用（落为 candidate）→ 队列清空 → 同一信封重发幂等 → 错误 token 拒绝 → 篡改信封留在队列 → B 反向推送 → 重启后队列仍在 → 队列上限触发背压。

证据：`docs/evidence/S05-v040-transport/http-relay.json`（`pass: true`，含 6 条边界说明）。
