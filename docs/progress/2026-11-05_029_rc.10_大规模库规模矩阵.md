# S05 rc.10 大规模库规模矩阵（r84）

> 时间：2026-11-05（Asia/Shanghai）。状态：**completed（合成库、本机、无模型调用）**。100/500/2000/5000 条合成记录的组装、列表、读取与写入耗时已测量；组装始终在 4096 字节预算内且确定性；发现每个 scope 的 4096 个 Markdown 文件事务上限，超过后写入会明确失败且不产生半写。G2/T04 的大规模数据项因此收窄，但真实设备分布与物理故障仍缺。

## 本轮目标与范围

r82/r83 关注并发与权限，但“大规模数据”一直只由 r14 的 2000 条渲染测量代表。本轮补齐：不同库规模下的注入组装（真实的 `registerInjectionAudit` 路径，含审计尝试）、列表、读取、写入耗时，以及预算截断和事务上限行为。只新建验证脚本；**未改产品代码、候选包或日常配置**。

脚本：`scripts/verification/scale-matrix.mjs`；证据：[result.json](../attachments/public-validation.md)，`ok: true`。

## 发现的规模边界

1. **每 scope 4096 个 Markdown 文件的事务上限**（`src/storage-safety.ts` 的 `MAX_FILES = 4096`、`MAX_TOTAL_BYTES = 32MB`）。5000 条时写入返回 `Scope exceeds transaction limit`，发生在 `captureScope` 阶段、journal 写入之前；因此**不产生半写、无 journal 残留**，读取/列表/组装仍正常。
2. **写入耗时随库线性增长**：从 r82 的约 46ms/条（20 条）到本轮的 397ms（100 条）、5865ms（2000 条）。原因是每次写都会完整快照整个 scope。`list` 同样随规模线性增长（2000 条约 2.4s，5000 条约 5.2s）。
3. 组装始终稳定在预算内：约 31 条入选、其余按相关性截断，说明预算保护与确定性没有随规模退化。

这些是**规模/性能边界而非数据损坏**：拒绝发生在事务开始前，错误清晰，库保持可读。对 v0.1.0 而言应在用户文档中写明“单个 scope 约 4000 条”的实操上限，并说明写入延迟在千条级会达到秒级。

## 对门槛的推进

- **T04（空库/规模）：** 从“2000 条有测量”推进到 100–5000 条的四档耗时矩阵，并明确 4096 文件事务上限与拒绝语义；真实设备分布、冷启动和 UI 路径仍未测。
- **G2：** 大规模数据不再只是“未测”，而是有明确上限与失败语义；物理磁盘满/断电与真实设备长时负载仍缺。

## 边界与未测

- 仅 Windows、本机、暖文件系统；合成中英文文本，未覆盖超大单条记录、项目/用户双 scope 混合、真实资料分布。
- 未测 UI 交互延迟、模型调用与 token 成本；组装字节只代表注入段大小。
- 5000 条拒绝写入是设计上限，不是本轮引入的回归；产品代码与 rc.10 包未改。回归：`typecheck` 通过，`npm test` **281/281**。

大规模库下的读取/组装行为稳定且受预算保护，写入与列表呈线性增长并在 4096 文件/scope 处明确拒绝。这为“真实数据前核验”和用户文档提供了量化依据。
