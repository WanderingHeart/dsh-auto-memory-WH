## 1. 动机

r132 的变更集是明文 JSON，任何拿到文件的人都能读取、伪造或替换。同步文件通过 U 盘/网盘/聊天工具传递时，至少需要回答三个问题：

1. 这份变更集是不是声称的发送方写的？
2. 我是否信任这个发送方？
3. 传输过程中内容有没有被看到或改动？

本项用本地密钥 + 签名 + 可选加密回答前两个问题和第三个问题的“改动”部分；不解决“隐藏元数据”与“传输层认证”。

## 2. 设计

### 2.1 设备身份

`src/device-identity.ts` 为每台设备生成两对密钥：

- Ed25519：签名与验签；
- X25519：ECDH 协商对称密钥。

`deviceId = "dev-" + sha256(signPublicKey) 前 16 个十六进制字符`，由签名公钥推导，不依赖本机名或随机数。身份文件保存公私钥（DER/base64）与创建时间；`saveIdentity` 以 `0600` 写入，但这是尽力而为，Windows 上不保证 ACL。

### 2.2 信任列表

`trust.json` 保存 `{deviceId, signPublicKey, encPublicKey, label?, addedAt}`。CLI 提供 add/remove/list。信任是**显式**的：接收方只解封信任列表内的发送方；公钥与信任记录不一致直接拒绝。没有“首次使用即信任”（TOFU），也没有撤销列表。

### 2.3 信封格式

`wh-sync-envelope` v1：

```json
{
  "format": "wh-sync-envelope",
  "version": 1,
  "sender": { "deviceId": "dev-…", "signPublicKey": "…", "encPublicKey": "…" },
  "recipient": { "deviceId": "dev-…" },
  "nonce": "…",
  "ciphertext": "…",
  "signature": "…"
}
```

发送流程：

1. 用 X25519 私钥与收件人加密公钥做 ECDH；
2. HKDF-SHA256（info=`wh-sync-v1`）导出 32 字节 AES-256-GCM 密钥；
3. 12 字节随机 nonce 加密变更集 JSON，密文尾部附 16 字节认证标签；
4. 对“去掉 signature 的信封规范化 JSON”做 Ed25519 签名。

接收流程依次校验：格式/版本 → 收件人是本设备 → 发送方在信任列表 → 发送方公钥与信任记录一致 → 签名 → 解密。任一失败都抛 `IdentityError` 并带稳定代码（`UNSUPPORTED_FORMAT`、`WRONG_RECIPIENT`、`UNTRUSTED_SENDER`、`KEY_MISMATCH`、`BAD_SIGNATURE`、`DECRYPT_FAILED`、`INVALID_ENVELOPE`）。

解出的变更集仍需 `verifyChangeset` 校验结构和校验和，再由 `sync-apply` 应用；信封不替代变更集自身的完整性校验。

## 3. 入口

### CLI（`src/maintenance-cli.ts`）

| 命令 | 作用 |
| --- | --- |
| `sync-init` | 生成身份文件（含私钥） |
| `sync-trust` | `add` / `remove` / `list` 信任设备 |
| `sync-seal` | 读取变更集，签名为指定收件人加密，写信封 |
| `sync-open` | 校验信任/签名/收件人后解封，写回变更集 |

身份与信任都是本地文件；没有服务端、没有账号、没有网络调用。

### 测试

`tests/device-identity.spec.ts`（7 项）：

- 身份生成、deviceId 与签名公钥一致、保存/加载往返；
- 信任添加/移除/缺失文件为空；
- 签+加密后正确收件人可解出同一变更集；
- 未信任发送方、错误收件人、篡改密文/签名、格式/版本非法、公钥与信任记录不一致均拒绝。

### 演练

`scripts/verification/sync-secure-drill.mjs`（8/8 PASS）：

1. 生成 A/B 身份并落盘；
2. 双向信任；
3. A 导出两条合成记录（一条 verified、一条 candidate）；
4. 封装给 B；B 解封得到同一变更集；
5. B 应用，两条均落为 candidate；
6. 篡改密文 → `BAD_SIGNATURE`；
7. 空信任列表 → `UNTRUSTED_SENDER`；
8. 第三方身份 → `WRONG_RECIPIENT`。

证据：`docs/evidence/S05-v040-sync/secure-drill.json`。

## 5. 边界与未做

- 没有传输层（HTTP/WebSocket/对象存储），文件交换仍由使用者负责；没有在线配对与二维码；
- 私钥是本地明文 JSON，没有 OS keychain、口令保护、硬件密钥；
- 没有密钥轮换、撤销列表、设备吊销、前向保密（静态 ECDH，长期密钥泄露会影响历史信封）；
- 加密只保护信封内容，不隐藏文件名、大小、时间与收发方 deviceId；
- 没有把身份/信任接入 API 或面板（只有 CLI）；面板仍展示单机状态；
- 解封后仍按 r132 的冲突策略执行；不做三方合并。
