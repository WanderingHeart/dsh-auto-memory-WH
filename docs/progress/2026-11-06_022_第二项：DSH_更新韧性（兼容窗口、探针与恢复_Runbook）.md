# S05 / v0.2.0 第二项：DSH 更新韧性（兼容窗口、探针与恢复 Runbook）

- 日期：2026-11-06
- 状态：实现完成，待切 v0.2.0 候选包
- 范围：`package.json`、`src/compat.ts`、`src/index.ts`、`tests/manifest-compat.spec.ts`、`tests/compat.spec.ts`、`scripts/verification/host-compat-check.mjs`、`scripts/verification/manual/backup-memory.ps1`、`docs/attachments/update-compatibility.md`、`docs/attachments/user-guide.md`、`docs/attachments/roadmap.md`、`docs/progress/2026-11-09_018_持久记忆_WH（dsh-auto-memory-wh）阶段总结报告.md`、`CHANGELOG.md`
- 边界：未改记忆读写逻辑（仅装载前自检）、未重建 `lib/`、未重打 0.1.0 冻结包、未在 DSH 0.3+ 上实测

## 1. 起因与目标语义

0.1.0 发布候选在 DSH 自动升级到 0.2.2-rc.1 后被整包跳过，侧栏入口消失（r117 定位并修复了声明方式）。所有者随后明确目标（2026-11-06）：

1. **非破坏性更新**：宿主升级后插件不应消失；旧行为继续工作，等插件更新后再适配新能力。
2. **破坏性更新**：记忆数据绝不损坏；允许入口短暂不可用，但必须可诊断、可恢复。
3. **边界**：不自动审核、不静默迁移、不删除记忆。

## 2. 机制

`@deepseek-ai/dsh-app-boot` 在启动时对 profile 的每个 bundle 执行 `evaluatePluginCompatibility`：

- 插件声明 `engines.dsh` 时只按该范围判定；否则逐个检查 `@deepseek-ai/dsh-*` peer 范围，二者都使用 `semver.satisfies(..., { includePrerelease: true })`。
- 不满足时整包被跳过并写入 `skippedBundles`；**不卸载、不触碰 `memory-wh`**。
- 宿主提供“精确版本豁免”（`compatibility.json`，键为 `包名@版本`），属于显式风险接受；当前 CLI 只把 `plugin` 参数转给 pnpm，没有独立 `allow-version` 子命令，因此文档以“安装覆盖新宿主的候选”为第一恢复路径。

因此：“更新就掉”的根因是窗口过窄，不是数据或安装损坏；要让非破坏性更新不掉，只能放宽窗口。

## 3. 实现

### 3.1 声明窗口

```json
"engines": { "dsh": ">=0.2.1-rc.5 <1.0.0" }
```

- 下限保留本地实测过的最早宿主，上限拒绝 1.0.0（未知大版本）。
- 由 `tests/manifest-compat.spec.ts` 守护：声明形式、覆盖 `0.2.1-rc.5`/`0.2.2-rc.1`、不声称 `1.0.0`/`1.1.0-rc.1`、仍拒绝 `0.1.5-rc.2`。

### 3.2 只读兼容探针

`scripts/verification/host-compat-check.mjs [profile] [stage]`：

- 读仓库 manifest、打包宿主版本、宿主 semver、profile bundle 列表、已安装插件 manifest 与 `compatibility.json`；
- 输出 `docs/evidence/<stage>/host-compat.json`（默认 `S05-v020-compat`）；
- 断言：窗口已声明、宿主版本可读、semver 可用、宿主在窗口内、bundle 已列出、已安装包存在、安装窗口覆盖宿主、豁免可读、`no-action-needed`；
- 失败时给出恢复建议（装新候选 / 精确豁免）；只读，不启动 DSH。

### 3.3 恢复 Runbook 与用户指南

- `docs/attachments/update-compatibility.md`：机制、更新前 30 秒检查、更新后恢复顺序（看日志→核实现场→装新候选/精确豁免/重装→验证）、数据安全边界、已知限制、与 0.1.0 事件的关系。
- `docs/attachments/user-guide.md` 新增 7.2“DSH 自动更新后插件消失怎么办”，明确“先别重装、别删 `memory-wh`”。

### 3.4 启动自检与降级

`src/compat.ts` 在 `apply` 最先执行只读能力检查（`tools.register`、`systemPrompt.section`、`ctx.on/effect/inject`，以及存在 web 连接时的 `connection.fetch.register`/`requestRejection`）：

- 有缺口时不启动记忆引擎、不触碰 `memory-wh`，只注册只读工具 `memory_wh_compat` 与只读路由 `/api/auto-memory-wh/compat.status`，并输出明确日志；
- 这样宿主改名/移除某个插件面 API 时，用户看到的是“能力不兼容”的诊断入口，而不是空白侧栏或无解释的半死状态；
- 检查是保守的：只判断形状，不猜测可用性。

### 3.5 更新前一条命令备份

新增 `scripts/verification/manual/backup-memory.ps1`：

- 默认 `~/.dsh/memory-wh` → `~/.dsh/backups/memory-wh-<时间>/`；
- 调维护 CLI 的 `backup`（含审计与归档），立即用 `verify` 复核，写 `backup-manifest.json`（快照 SHA-256、文件数、边界说明）；
- DSH 运行中默认拒绝（`-AllowRunningDsh` 可显式接受风险）；`-CheckOnly` 只读预检；
- 已在合成根上实跑：9 文件、快照 `d6a610503594b4f45f514342013efe474d0535954ee17ad85db513b083002a92`、verify 通过。

## 5. 边界与风险

- `engines.dsh` 只表达“愿意尝试装载”，不能证明宿主 API 行为一致；宽窗口把未知风险留给运行时。
- 未在 0.3+ 上实测；大版本更新后仍应跑探针与面板冒烟。
- 精确豁免不会随宿主升级自动扩展，忘记移除会掩盖后续不兼容。
- 本项不改运行时加载逻辑；若未来宿主 API 真发生破坏性变化，仍需按 runbook 回退或发布适配版本。
