# S05 rc.11 真实升级故障恢复验收（r110）

- 时间：2026-11-06
- 状态：隔离副本上通过；产品代码与候选包未改动
- 依据：`docs/progress/2026-11-06_018_发行前门槛清单.md`（T17/G4）、`docs/progress/2026-11-06_001_一次性验收清单（0.1.0_最终候选；文内历史链接仍指向_rc.11_阶段报告）.md`
- 候选包：`0.1.0-rc.11`（`0AEC562A…72CB3B49`）

## 起因

r91 只演练了**截断包导致安装失败**，失败发生在解包阶段，属于“坏的输入”，不是“真实升级过程中断”。G4 剩下的缺口是：从已安装的旧版本真正升级到新版本时，如果进程被杀、或升级到一半旧包已移除而新包未就位，记忆是否仍然安全、能否用同一条升级命令恢复。

## 方法

`scripts/verification/upgrade-fault-recovery.mjs`：

1. 复制隔离安装家 `.work/S05/installation-home` 到 `.work/S05/upgrade-fault-home`，按 r91 的做法改写 `profiles/wh-s05/node_modules/.modules.yaml` 里的 store 路径；**设置 `DSH_HOME` 指向副本**，避免 CLI 改到真实 home（首次运行未设时曾误建 `~/.dsh/profiles/wh-s05`，已删除并核对真实 profiles 仅剩 `desktop`/`web`）。
2. 用 `remove` + `add rc.10` 把副本降到 rc.10（真实版本跨度），记录 `memory-wh` 的 9 个文件哈希与锁/journal 状态。
3. 故障 A：启动 `dsh plugin add rc.11`，约 450ms 后用 `taskkill /T /F` 杀进程；随后核对版本仍为 rc.10、记忆逐字节不变；再用同一条 `add rc.11` 恢复。
4. 故障 B：模拟“升级到一半、旧包已移除、新包未就位”——直接删除副本里的 `node_modules/dsh-auto-memory-wh`；核对记忆不变、bundle 缺失；再跑同一条 `add rc.11` 修复。
5. 恢复后跑宿主生命周期探针 `installed-active-session-lifecycle.cjs 0.1.0-rc.11 S05-rc11-fault upgrade-fault-home wh-s05`，证明升级后的包能被打包宿主真实加载。

## 观察

- 升级过程只改 profile 的 `node_modules` 与 lockfile，**不触碰 `memory-wh`**；因此进程中断或 bundle 缺失时，记忆天然不受影响。
- 同一条 `add rc.11` 对“已装旧版”和“bundle 缺失”两种状态都能修复，不需要先 `remove`；这比“先卸载再装”的步骤更接近用户实际升级路径。
- 安装耗时约 0.8–1.3s，故障窗口很短；本轮用 450ms 确实抓到了安装中段（退出码 1、版本未变）。

## 边界

- 隔离副本、合成记忆；没有升级真实用户的插件目录或真实记忆。
- 故障是**进程终止**与**bundle 缺失**，不是升级中掉电；升级阶段的物理掉电未测（断电已由 r100 覆盖记忆写入，二者不同）。
- 时间窗口依赖机器速度；报告记录的是本轮实测时序。
- 首次运行曾因未设 `DSH_HOME` 在真实 home 建过 `wh-s05` 测试 profile，已删除并确认不影响 `desktop`/`web`。
