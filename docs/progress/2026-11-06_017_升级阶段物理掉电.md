# S05 0.1.0 升级阶段物理掉电

更新：2026-11-06。范围：S05 / 本地私有候选 `0.1.0`。状态：通过（隔离 VM + 合成数据）。关联：[发行前清单](2026-11-06_018_发行前门槛清单.md)、[一次性验收清单](2026-11-06_001_一次性验收清单（0.1.0_最终候选；文内历史链接仍指向_rc.11_阶段报告）.md)、[用户指南](../attachments/user-guide.md)。

## 起因

G4 的最后一项现场缺口是“升级进行中被物理断电”。r91 演练了截断包导致的失败安装，r110 演练了升级进程被杀与半安装缺失，但两者都不是硬断电：操作系统与 NTFS 仍有机会把缓存写回磁盘。本轮在 VirtualBox + Windows 10 客户机上，于 `dsh plugin add 0.1.0` 升级进行中由宿主机强制 `poweroff`，观察升级 home 与记忆数据的最终状态，并验证能否修复。

## 方法

- **便携运行环境**：不重装桌面，而是从 `C:\DeepSeek Harness\resources\app.asar\dsh` 提取 `dsh/` 树（293,107,893 字节）并复制 `resources/runtime`（约 270 MB），客户机用自带 Node 24.22 直接运行 `dsh-desktop-host/lib/cli.js`（同版本 0.2.1-rc.5）。边界：这是 CLI，不是桌面 UI。
- **测试 home**：复制隔离安装 home 到 `.work/S05/powerloss-upgrade`，改写 `.modules.yaml` 路径，用便携 CLI 降级安装 `0.1.0-rc.11`；记忆 9 个文件、9,632 字节。升级目标为 `0.1.0` 候选包（101,558 字节，SHA-256 `9AC97A5C…A35C39`）。
- **编排**：把 portable CLI、home、`plugin.tgz` 与脚本打包为 `wh-kit.zip`（246,296,760 字节），经宿主机 `127.0.0.1:8000` 由客户机 `10.0.2.2:8000` 下载；客户机在启动升级前上传 `upgrade-start.json`，宿主机轮询到标记后 500 ms 执行 `VBoxManage controlvm WH-PowerLoss poweroff`。
- 全部数据为合成记录；未接触日常记忆、凭据或发布物。

## 结果

| 项 | 观测 |
|---|---|
| 断电时刻 | `2026-11-06T12:36:28.384Z`，标记后约 500 ms，升级约 1.1 s 时切断 |

证据：`docs/evidence/S05-0.1.0-upgrade-power-loss/{repair-result.json,corrupt-modules.json,upgrade-start.json}`。`repair-result.json` 记录 `pass: true`、`at 2026-11-06T11:52:09.956Z`、`manifestHeadBefore EF BB BF 7B 0D 0A` → `manifestHeadAfter 7B 0A 20`、`add exit=0`、`version=0.1.0`、`baseline=9 actual=9`。

## 观察

1. **零填充不是截断。** `.modules.yaml` 长度完整保留、内容全部为零，说明断电发生在 NTFS 为文件分配长度之后、数据落盘之前。修复脚本必须假定“文件看似存在但内容不可用”，不能只检查长度。
2. **升级失败不会碰记忆。** 升级步骤先更新 profile 元数据，再落插件文件；断电落在元数据阶段，9 个记忆文件未变。这与 r91“失败早于写入”的结论一致。
3. **修复路径可重复。** 删除损坏的 `.modules.yaml`/`pnpm-lock.yaml`、写回干净 manifest、重跑同一条 `add` 即恢复；无需重装 Node、无需删记忆。报告中的 BOM 问题是**验证脚本自身**用了 PowerShell 5.1 带 BOM 的 `Set-Content` 造成的，不是插件缺陷；最终用无 BOM UTF-8 写入解决。
4. **边界**：CLI 而非桌面 UI；合成 home；单次断电；修复由所有者手工执行；没有验证“断电恰逢记忆文件写入”的窗口（该窗口由 r54/r91/r99 的进程中断与断电演练覆盖）。
