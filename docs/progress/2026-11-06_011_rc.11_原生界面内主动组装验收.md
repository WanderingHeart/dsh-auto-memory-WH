## 起因

r90 的原生桌面验收覆盖了安装、面板编辑/审核/置顶/静音/归档恢复与卸载，但那次会话没有触发新的组装，因此“在真实原生界面里主动发一条消息、让 WH 注入并让模型收到”一直未验证；r106 已用真实账号路由在 headless 路径上证明模型接收，但仍缺原生 UI 这一层。

r107（CDP 网络层阻断原生断连）与 r108（保存派发后动态关闭）证明了“失败路径”的存储安全，这一轮补“成功路径”：用真实桌面输入框发送消息。

## 方法

1. 在隔离 home（`.work/S05/native-real-user-home`）写入一条合成用户记录 `native-active-assembly-receipt`（`verified`、正文明确标注“仅隔离验收用”）。离线预览确认它将进入索引（546 字节）。
2. 复制 r90 的隔离 `user-data`，以 `dsh-app://app/` 页面启动桌面实例，并开启 `--remote-debugging-port=9222`。
3. 启动本机 mock 模型（`127.0.0.1:8931`，Anthropic Messages + SSE），通过临时 `cordis.patch.yml` 把 `llm-deepseek.baseURL` 指向它，`DEEPSEEK_API_KEY=dummy`；运行结束后恢复原 patch。
4. 用 CDP 定位真实输入框 `[data-composer-input]`（Lexical `contenteditable` div），聚焦、`Input.insertText` 输入提示词、派发 Enter。
5. 等待 mock 收到请求、审计新增 `render_attempt`、界面出现助手回复；写证据 `docs/evidence/S05-rc11-native-active-assembly/active-assembly.json`。

## 观察

- `deepseek-flash` 的 `systemPromptUpdate` 是 `in-history`：记忆索引随历史中的 system 消息发送，因此 mock 记录里 `system` 字段为 `null`，标记出现在 messages 内容中——这是适配器的正常路径，不是注入缺失。
- 本次注入两条记录：恢复的合成会话 cwd 属于项目作用域（`native-audit-reviewed-r72`），以及用户作用域的新合成记录。
- 审计新增一条 `render_attempt`，`injected` 与模型请求中的两条记忆一致；审计仍只代表“组装尝试”，最终接收由 mock 收到的请求证明。
- 请求体很大（含工具 schema 等），说明注入发生在真实的宿主请求里，而不是旁路生成的文本。

## 边界

- 模型是本机 mock，不是真实 DeepSeek（真实模型接收见 r106）；本轮验证的是“原生 UI → 宿主组装 → 请求携带记忆”的链路。
