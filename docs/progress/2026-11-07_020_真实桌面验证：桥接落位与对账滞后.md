# r146 — v0.5.1 真实桌面验证：桥接落位与对账滞后

- 日期：2026-11-07
- 阶段：S05 / v0.5.1（已切版、21/21、桌面已升级）
- 前置报告：[r145](2026-11-07_019_日常桌面升级.md)、[r144](2026-11-07_018_切版、候选包与隔离_21_21.md)、[r143](2026-11-07_017_真实宿主投递核对_+_任务完成即归档.md)
- 后续：[r147](2026-11-07_021_任务一变立即对账.md)（立即对账）

## 1. 目的

0.5.1 装上日常 `desktop` 并重启后，验证“任务 → 宿主调度 → 到点投递 / 完成清理”在真实宿主上成立，重点看两件事：

1. 新建任务后，桥接是否把任务写入宿主 `schedule.json`；
2. 在面板“标记完成”后，归档删除与宿主任务清理是否符合预期。

## 2. 方法

- 桌面环境：`~/.dsh/profiles/desktop`，`dsh-auto-memory-wh` 0.5.1（`lib/index.js` `F3F7…940A`），DSH 于 20:05:25 重启（GUI `http://127.0.0.1:52198`）。
- 用 `.work/create-verify-051-task.mjs` 直接走存储层创建 user scope 任务（会话工具里没有 `memory_write`）：

  | 字段 | 值 |
  | --- | --- |
  | name | `verify-051-archive` |
  | title | 验证 0.5.1 完成即归档 |
  | type | task |
  | dueAt / remindAt | `1794056400000`（2026-11-07T13:00:00Z = 21:00 本地） |
  | priority | 2 |
  | taskStatus | open |
  | status | verified |

  创建时刻 20:07:25，revision `fb6e75af68c1f4e3ccc66cc5383dddc8d9ced7679e4eb833a2df96960166ee87`。
- 用 `.work/poll-bridge-051.mjs` 轮询 `~/.dsh/storages/schedule.json` 与 `~/.dsh/memory-wh/schedule-bridge.json`，观察宿主侧变化。

## 3. 观察结果

- **20:10:27**，宿主 `schedule.json` 出现新任务 `schedule-6586cd97-8f35-40d8-afca-da8fc62e28ec`：
  - `kind: at`、`scheduledAt: 2026-11-07T13:00:00Z`、`status: active`、`target: new_once`；
  - 标题 `记忆提醒：验证 0.5.1 完成即归档`；
  - prompt 首行 `[memory-wh] task=verify-051-archive`；
  - `involvedSessionIds` 记为 `session-b3db222c…`（预占的投递目标）。
- 同一时刻 sidecar 写入 `entries["verify-051-archive"]`：`scheduleId` 同上，`signature` 含 `name/title/description/priority/remindAt/dueAt`，`syncedAt` `1794053427099`。
- 任务文件仍在活跃列表（20:15 复查 `taskStatus: open`），用户尚未点击“标记完成”。

## 4. 发现：对账滞后约 3 分钟

任务创建 20:07:25 → 宿主落位 20:10:27，滞后约 3 分钟。原因是 0.5.1 的对账只有三种触发：

1. 插件启动后 10 秒一次；
2. 每 5 分钟一次定时器；
3. `agent/created` 事件（60 秒节流）。

任务创建发生在启动对账之后，因此只能等下一次定时器或下一次新会话。直接后果：

- **提前完成的任务仍可能被提醒**：用户创建任务后很快标记完成，而下一次对账还没跑，宿主侧任务仍处于 `active`；若到期时间落在两次对账之间，宿主仍会按计划投递。
- 完成后的宿主清理同样最多滞后 5 分钟。

0.5.1 的“完成即归档”只保证记忆侧立即归档，宿主侧清理仍依赖下一次对账。这是本次真实桌面验证暴露的行为缺口。

## 5. 决定

- 不在 0.5.1 上继续点击验证这个滞后行为（会人为制造一次可能误投递的等待）。
- 直接实现 **0.5.2：任务一变立即对账**（写入/审核/完成归档/删除成功后立即触发一次 reconcile），并把“重启后点击 标记完成 → 宿主任务立即清空 → 21:00 不投递”作为 0.5.2 的真实验收项，见 [r147](2026-11-07_021_任务一变立即对账.md)。
- 本报告结论以“桥接在真实宿主上成功创建调度任务”为界；到点投递与完成清理的真实点击验证移到 0.5.2。

## 6. 边界与未覆盖

- 单机、单次观察；宿主 `schedule` 仍是内部服务（无公开 `.d.ts`），宿主升级可能改变行为。
- 本任务在 21:00 前若被完成，则不会真正投递；本报告不声称验证了“到点投递”的第二次实例（首次实例见 r143 的 `host-delivery.json`）。
- `schedule.json` 不在 WH 的备份范围内；sidecar 丢失最多导致一次重复调度，不会丢任务真源。
